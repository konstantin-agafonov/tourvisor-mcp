> Статус: план, реализация не начата. Файл: `SCRAPING_PLAN.md` в корне проекта.
> Дата: 23.10.2026. Окно работы: **48 часов с момента старта прогонов**.
> Родственный документ: `PLAN.md` (MCP-сервер) — переиспользуем его ядро (playwright-daemon,
> parsers, cache), но здесь это автономный скрапер, без MCP-интерфейса.

---

## 1. Цель

За 48 часов собрать с сайта `https://tourvisor.ru/` и сохранить:

1. **Справочники** (полные значения): города вылета, страны, курорты (+subregions), отели,
   туроператоры, типы питания, звёздность.
2. **Туры**: все доступные предложения с поиском под жёстко зафиксированные параметры.
3. **Отели**: полная информация по тем отелям, которые попали в эту выдачу
   (описания, удобства, галереи, рейтинги, **отзывы** с текстами).

### Жёсткие фильтры поиска (весь период сбора не меняются)

| Параметр | Значение |
| --- | --- |
| Город вылета | **Только Москва** (tourvisor code = 2, проверить в M0) |
| Дата вылета | **ровно 01.11.2026** (`datefrom = dateto = 01.11.2026`) |
| Длительность | **ровно 14 ночей** (`nightsfrom = nightsto = 14`) |
| Звёздность | **только 5★** |
| Туристы | **2 взрослых, 0 детей** |

### Что НЕ собираем (по ТЗ)

- Перелёты (расписание чартеров, отдельные блоки рейсов) — только то, что является частью
  карточки тура, если она необходима для идентификации тура (без детального разбора).
- Горящие туры.
- Городов вылета кроме Москвы нет; дат кроме 01.11.2026 нет; других сроков/звёздности/
  составов туристов нет.

Направления: **все страны** из справочника (те, что дают выдачу под эти фильтры). Обход — по странам, т.к. поиск на сайте всегда под одну страну.

## 2. Оценка объёма и бюджет времени (48 ч)

Делать расчёт **после M0-разведки**, но стартовые допущения:

| Сущность | Ожидание | Интервал запросов | Бюджет |
| --- | --- | --- | --- |
| Справочники | ~15–25 запросов (в т.ч. отели по странам/курортам) | 2 s | ~1 мин |
| Отели 5★ в выдаче | 1.5–4 тыс. уникальных | — | — |
| Поисковая сессия (туры) | батч отелей (сколько позволят форма/URL — уточнить в M0, ориентир 20–50), на страну | 60–180 s на сессию + ~5–15 s на парс | ~3–8 ч на все страны |
| Детали отеля (описание/галерея) | по 1 запросу на отель | 2.5 s | 2–4 ч |
| Отзывы | paginated; **главная неопределённость объёма** (десятки–сотни страниц на отель) | 2.5 s | см. §8 «правила усечения» |
| Изображения | 10–30 на отель + фото туров; CDN `img.tourvisor.ru` — прямой fetch без playwright | пул 4–6, 0.5 s | 2–4 ч |

Вывод: критически узкое место — **отзывы**. Правило: сначала все отели покрываются
«минимальным гарантированным» набором (первая страница отзывов), затем догоняем остальное
по очереди остатков — см. §8.

## 3. M0 — разведка (таймбокс 2–3 ч, до начала массового сбора)

Через playwright (detached-режим по `PLAN.md` §2.1, профиль `data/profile`) снять:

1. **Справочники**: откуда сайт берёт списки (options селектов, embed-конфиг модуля,
   XHR JSON). Зафиксировать конвертацию id/name для: departures (Москвы id), стран,
   курортов, турапоператоров, meals, звёзд.
2. **Поиск с URL-параметрами**: умеет ли `search.php` принимать прямые query-параметры
   (`dep/cou/datefrom/dateto/nights/adults/stars/hotels=...`) — это резко удешевляет
   обход. Проверить поддержку: (`а`) батча hotel id в одном поиске, (`б`) фильтра
   «5 звёзд» прямо в параметрах, (`в`) только 2 взрослых.
3. **Выдача**: признак завершения асинхронного поиска (исчезновение лоадера / progress=100,
   статусы операторов), селекторы карточки отеля в выдаче, где лежат мин. цена, туры,
   изображение, ссылка на отель и число отзывов.
4. **Страница отеля**: URL-формат, блоки описания, удобств, координат, галереи
   (включая lazy-load), рейтингов.
5. **Отзывы**: как грузятся (встроенные в страницу / пагинация / XHR JSON с
   `hotelcode`), есть ли полностью весь список одним запросом — это определяет
   весь бюджет (§2).
6. **Лимиты/антибот**: поведение при 40 запросах подряд (2 s интервал), наличие капчи,
   редиректов, «Access denied». Зафиксировать стоп-сигналы.

Выхлоп: `docs/recon-scraping.md` с XHR/параметрами/селекторами + по одному HTML-снапшоту
каждого типа страницы в `test/fixtures/` (нужны для тестов парсеров без сети).

## 4. Хранение: SQLite `data/tv.db` (полунормализованная схема)

```sql
-- Нормализованная часть
CREATE TABLE countries   (id INTEGER PRIMARY KEY, name TEXT, raw JSON);
CREATE TABLE resorts     (id INTEGER PRIMARY KEY, country_id INTEGER, name TEXT, subregions JSON);
CREATE TABLE operators   (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE meals       (id INTEGER PRIMARY KEY, code TEXT, name TEXT);
CREATE TABLE dictionaries(key TEXT PRIMARY KEY, payload JSON, fetched_at INT);  -- сырые списки (departures, stars...)

CREATE TABLE hotels (
  hotelcode TEXT PRIMARY KEY,           -- ключ tourvisor для отеля
  country_id INT, resort_id INT, subregion_id INT,
  name TEXT, stars INT, address TEXT, coords TEXT,
  description TEXT, facilities JSON,    -- удобства/услуги (сырой список)
  rating REAL, rating_breakdown JSON,   -- общий и по критериям
  reviews_count INT, images_count INT,
  raw JSON,                             -- полный сырой payload страницы/объекта
  captured_at INT, updated_at INT
);

CREATE TABLE tours (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  hotelcode TEXT REFERENCES hotels,
  operator_id INT, price REAL, currency TEXT DEFAULT 'RUB',
  departure_date TEXT DEFAULT '2026-11-01', nights INT DEFAULT 14,
  adults INT DEFAULT 2, children INT DEFAULT 0,
  room TEXT, meal_id INT, room_category TEXT,
  flight_json JSON,                     -- только идентификация рейса (без парсинга перелётов)
  raw JSON, captured_at INT,
  UNIQUE(hotelcode, operator_id, price, departure_date, room, meal_id, flight_json)
);

CREATE TABLE reviews (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  hotelcode TEXT REFERENCES hotels,
  author TEXT, date TEXT, rating REAL, score_breakdown JSON,
  positives TEXT, negatives TEXT, text TEXT,
  raw JSON,
  fetched_page INT, captured_at INT,
  UNIQUE(hotelcode, hash)               -- hash = sha1(text+date+author)
);

-- Изображения: файлы на диске, индекс в БД (§5)
CREATE TABLE images (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  subject_type TEXT CHECK(subject_type IN ('hotel','tour','review')),
  subject_key TEXT,                     -- hotelcode / tour id
  kind TEXT,                            -- card / gallery / room / tour_full ...
  source_url TEXT, local_path TEXT, sha256 TEXT,
  mime TEXT, bytes INT, width INT, height INT, status TEXT,
  UNIQUE(subject_type, subject_key, source_url)
);

-- Очередь и журнал: источник возобновляемости всего пайплайна
CREATE TABLE jobs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  type TEXT,                            -- dict | tours_search | hotel_details | hotel_reviews | images
  payload JSON, status TEXT DEFAULT 'pending',  -- pending|running|done|error|skipped
  tries INT DEFAULT 0, last_error TEXT, started_at INT, finished_at INT,
  priority INT DEFAULT 100, payload_jkey TEXT, UNIQUE(type, payload_jkey)
  -- payload_jkey = sha1 массива payload; защищает от дублей задач при рестартах
);
CREATE TABLE runs (id INTEGER PRIMARY KEY, type TEXT, started_at INT, finished_at INT, stats JSON, error TEXT);

PRAGMA journal_mode = WAL; PRAGMA synchronous = NORMAL;
```

Справочники тоже дублируются в нормализованных таблицах, чтобы фильтрация/отчёты делались
SQL-ом, а не разбором JSON.

## 5. Изображения: файлы на диске

- Корень: `data/images/`; структура `data/images/{country_id}/{resort_id}/{resort_id}_{hotelcode}/…`.
- Имя файла: `{kind}-NNN{.ext}` где `kind ∈ {card, gallery, room, tour}` (ext из content-type;
  по умолчанию jpg).
- Дедуп: `sha256` → если совпадает с уже скачанным, храним одиночную копию, второй путь
  делаем жёсткой ссылкой (`fs.link`) или просто скипаем (индекс уже уникален по `source_url`).
- Скачивание: **без playwright** — прямой fetch на CDN c корректным `Referer: https://tourvisor.ru/`
  и `User-Agent`, пул 4–6 параллельных, таймаут 20 s.
  - Ловим 403/429 → временный откат (defer job + экспоненциальный бэкофф), не валить очередь.
- Лимиты: файлы < 100 KB или > 15 MB — помечать `status=suspect` в `images`; битые/пустые
  файлы — `status=bad`.
- Фото туров: почти всегда те же фото отелей, что и в галерее — дедуп по sha256 обязан
  схлопнуть дубликаты; при этом обязательна хотя бы 1 картинка на тур (снята из карточки выдачи).

## 6. Раннер и устойчивость (главная техническая часть плана)

Один процесс `src/scraper/runner.ts` (Node ≥ 20, TS):

- **Playwright**: 1 браузер из detached-daemon (профиль `data/profile`), вкладки sequential,
  внутри одного браузера — не параллелить больше 2 вкладок на сайт (политичность + chattiness).
- **Очередь в SQLite** (`jobs`): единственный источник правды; любой сбой/рестарт →
  `running`-задачи старше 10 мин переводятся в `pending`; `done`-пометки пишутся транзакционно
  с данными — сбор идемпотентен, рестарт без потерь и дублей.
- **Ретраи**: сеть/таймаут ×3 (2 s → 8 s → 30 s); страница отдаёт капчу/бан →
  глобальная пауза 10 мин + N-е подряд событие = **hard-stop** с уведомлением (§8).
- **Интервал**: базовый 2 s между запросами к сайту; jitter ±0.5 s; для CDN картинок — свой пул.
- **Чекпоинт-статистика** раз в 5 мин → `runs.stats` + вывод в консоль/файл `logs/scraper.log`:
  сколько отелей закэшировано/детали/отзывы/картинки, скорость, прогноз до завершения.
- **Остановка**: `Ctrl+C` / `pnpm scrape resume` — продолжение с очереди; опция
  `--timeout` (жёсткий дедлайн 46 ч: мягкая финализация = остановить новые отзывы, добрать
  изображения, закрыть отчёт).

## 8. Правила усечения объёма (для отзывов — главный риск)

1. **Гарант**: ≥ 1 страница отзывов (обычно 10–20 отзывов) обязана быть на **каждом**
   отеле; это приоритет 10.
2. Далее волны по критериям: приоритет 20 = отели с наибольшим `rating` и наибольшим числом отзывов,
   приоритет 30 = отели с наибольшим числом туров; идут до исчерпания дедлайна.
3. Каждый отзыв хранится с `fetched_page` → после дедлайна в отчёте видно, у каких отелей
   отзывы получены частично (метрика «отзывы_count против fetched»).
4. Если в M0 окажется, что отзывы летят **одним XHR-JSON на отель** — проблема снимается
   целиком: §2-бюджет отзывов падает до пары часов и усечение не нужно.

## 9. Качество и контроль

- **Тесты парсеров** на fixtures (M0) — без сети; при рестарте сборки они же отпускают
  в бой, если сайта нет.
- **Спот-чек после Ф4/Ф5**: 10 случайных отелей — сверить руками (звёздность и имя, цена
  карточки против `tours`, кол-во фото, наличие текста отзывов).
- **Агрегаты в отчёте** (`docs/scrape-report.md`, генерится скриптом):
  - отели: всего / с деталями / с ≥1 фото / со звёздностью ≠ 5 (аномалии);
  - туры: всего / медиана/мин цена по странам; пустые страны;
  - отзывы: всего / уникальных / распределение по отелям; отели с 0 текстов;
  - изображения: total/dedup/ошибки/по kind;
  - тайминги: сек/запрос, дата начала/конца.
- **Экспорты** (доп. если время позволит): `reports/tours.csv`, `reports/hotels.csv`,
  административные SQL-агрегаты (вью/дампов).

## 10. Риски и правила остановки

| Риск | Митигация |
| --- | --- |
| Капча/блокировка после N запросов | мягкий график (2 s), уважение к 429/503, hard-stop после 3 неудачных пауз |
| Объём отзывов слишком велик, не влезает в бюджет | §8: гарантия-минимум + волны приоритетов + отчёт о непокрытии |
| Смена разметки в середине сбора | fixtures-тесты и single-source селекторы; поломка → скип задачи + тревога, не остановка всего |
| Урезанная публичная выдача (5★/14 ночей вне модуля) | M0 до всего остального; при недоступности фильтров в UI — прямой URL-параметр; если не выйдет — альтернативный путь «поиск всей страны + пост-фильтр 5★/14 ночей в парсере» |
| Диск: 20–80k изображений | структура каталогов по странам/курортам; размер БД оценивается на Ф3; при узком месте — режим images-only |
| Сбой сети/недоступность сайта | лог + resume; все повторы через `jobs`, человеко-читаемый лог |

## 11. Критерии приёмки

1. SQLite-файл `data/tv.db` содержит: полные словари (departures/countries/resorts/
   операторы/meals) и отели 5★, все туры по заданным фильтрам, отели с полными описаниями.
2. Каждый отель из выдачи имеет ≥ 1 страницу отзывов; показатель покрытия отзывов
   ≥ 90 % отелей (по числу отелей, не текстов; полный текст всех страниц — по факту
   доступного бюджета, иначе отчёт с точным покрытием).
3. `data/images/…` содержит файлы (не blob'ы) со структурой §5; каждый файл имеет строку
   в `images` с указанием его `subject_key`; ≥ 1 изображение на каждый отель.
4. Отчёт `docs/scrape-report.md` содержит все величины из §9, а также отражает любые
   пропуски (страна/отель/отзывы), которые не удалось покрыть, с причинами.
5. Перезапуск после случайного kill в любом месте не ломает очередность и не
   дублирует данные (проверяется тестом и на практике одной сетевой ошибкой).
6. Никакие данные вне фильтров (другие даты/звёзды/составы/горящие/перелёты) не попадают в БД.
